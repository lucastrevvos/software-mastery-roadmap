BLOCO 1 · HTTP SÍNCRONO

Primeiro sentimos o custo da rede

Cliente → Orders → HTTP → Payments

Experimentos concluídos: serviço indisponível, timeout, latência controlada, retry e perda de resposta.

Descoberta: timeout não significa necessariamente que a dependência morreu; significa que o chamador não obteve resposta dentro do limite aceito.
HTTP síncrono: simples e direto, porém acopla disponibilidade e latência entre serviços.

      ▼
payments_dead_queue

BLOCO 5 · CONCORRÊNCIA

SELECT → INSERT mostrou uma race condition

A: SELECT → não existe
B: SELECT → não existe
A: INSERT ✅
B: INSERT ❌ 23505
UNIQUE protegeu o dado, mas a segunda requisição recebeu erro 500. A constraint manteve a invariante, porém a experiência da aplicação ainda estava errada.

Correção

INSERT ...
ON CONFLICT (order_id)
DO NOTHING
RETURNING ...

Resultado comprovado com duas chamadas concorrentes:

DB PAYMENT CREATED: ...
CONCURRENT IDEMPOTENT HIT: ...
Modelo mental: prefira invariantes no banco e operações atômicas antes de introduzir locks explícitos.

BLOCO 6 · AT-LEAST-ONCE

Persistiu, morreu antes do ACK, recebeu de novo

RabbitMQ entrega
↓
Payments salva no PostgreSQL ✅
↓
processo consumer morre antes do ACK 💥
↓
RabbitMQ devolve a mensagem para ready
↓
Payments volta
↓
REDELIVERED: true
↓
IDEMPOTENT HIT
↓
ACK ✅
Evidência: com a aplicação consumer morta, a queue ficou messages_ready=1, messages_unacknowledged=0, consumers=0. Após reiniciar Payments, a mensagem voltou com REDELIVERED: true e foi confirmada sem duplicar o registro.
Princípio: at-least-once delivery exige consumer idempotente.

BLOCO 7 · RETRY COM DELAY

Saindo do hot retry para fila de espera

payments_queue
  -- NACK requeue=false --> payments.retry
  --> payments_retry_5s
  -- TTL 5000ms / expired --> payments.return
  --> payments_queue

DLXTTLx-deathNACK requeue=false

Comandos executados

docker compose exec rabbitmq rabbitmqctl clear_policy payments-dlxRemove temporariamente a policy antiga que enviava a main queue direto para a DLQ final.
curl -u app:app -X PUT http://localhost:15672/api/exchanges/%2F/payments.retry -H "Content-Type: application/json" -d '{"type":"direct","durable":true,"auto_delete":false,"internal":false,"arguments":{}}'Cria exchange de retry.
curl -u app:app -X PUT http://localhost:15672/api/exchanges/%2F/payments.return -H "Content-Type: application/json" -d '{"type":"direct","durable":true,"auto_delete":false,"internal":false,"arguments":{}}'Cria exchange de retorno.
curl -u app:app -X PUT http://localhost:15672/api/queues/%2F/payments_retry_5s -H "Content-Type: application/json" -d '{"durable":true,"auto_delete":false,"arguments":{}}'Cria fila de espera de 5 segundos.
curl -u app:app -X POST http://localhost:15672/api/bindings/%2F/e/payments.retry/q/payments_retry_5s -H "Content-Type: application/json" -d '{"routing_key":"payments.retry","arguments":{}}'Binding retry exchange → retry queue.
curl -u app:app -X POST http://localhost:15672/api/bindings/%2F/e/payments.return/q/payments_queue -H "Content-Type: application/json" -d '{"routing_key":"payments.return","arguments":{}}'Binding return exchange → main queue.
docker compose exec rabbitmq rabbitmqctl set_policy payments-retry-5s "^payments_retry_5s$" '{"message-ttl":5000,"dead-letter-exchange":"payments.return","dead-letter-routing-key":"payments.return"}' --apply-to queues --priority 20TTL 5s; depois expira e retorna para processamento.
docker compose exec rabbitmq rabbitmqctl set_policy payments-main-retry "^payments_queue$" '{"dead-letter-exchange":"payments.retry","dead-letter-routing-key":"payments.retry"}' --apply-to queues --priority 20Falha na main queue passa a seguir para o retry exchange.
docker compose exec rabbitmq rabbitmqctl list_exchanges name typeValidação da topologia.
docker compose exec rabbitmq rabbitmqctl list_bindings source_name destination_name destination_kind routing_keyValidação dos bindings.
docker compose exec rabbitmq rabbitmqctl list_policiesValidação das policies.
docker compose exec rabbitmq rabbitmqctl list_queues name messages_ready messages_unacknowledged consumersObserva a mensagem estacionada no retry e depois retornando.

Primeiro teste comprovado

19:17:04.337  SIMULATED TRANSIENT FAILURE
~5 segundos
19:17:09.344  RETRY ARRIVED AFTER DELAY
PROCESS PAYMENT
DB PAYMENT CREATED
MESSAGE ACKED

O header x-death registrou:

payments_queue      reason=rejected count=1
payments_retry_5s   reason=expired  count=1
Importante: REDELIVERED permaneceu false. Para retries baseados em DLX/TTL, o histórico útil está em x-death.
Por que não usar sleep(5000)? A fila segura a mensagem e libera o worker. Dormir dentro do consumer manteria o trabalho preso e reduziria capacidade.

CHECKPOINT ATUAL · 15/09/2026

Contador de retry agora vem do RabbitMQ

Removemos a dependência conceitual de um contador local e extraímos retryCount de x-death.

const mainQueueDeath = xDeath.find(
  death => death.queue === 'payments_queue' && death.reason === 'rejected'
);

const retryCount = Number(mainQueueDeath?.count ?? 0);

Resultado observado

RETRY COUNT: 0
SIMULATED TRANSIENT FAILURE - attempt 1
↓ ~5s
RETRY COUNT: 1
SIMULATED TRANSIENT FAILURE - attempt 2
↓ ~5s
RETRY COUNT: 2
TRANSIENT FAILURE RECOVERED AFTER RETRIES
PROCESS PAYMENT
DB PAYMENT CREATED
MESSAGE ACKED

O x-death evoluiu para count:2 tanto no rejected da main queue quanto no expired da retry queue.

Conclusão comprovada: o histórico de retry sobrevive fora do processo da aplicação e pode ser usado por múltiplas réplicas. Não precisamos de failureAttempts Map para saber em qual tentativa a mensagem está.

DECISÕES ARQUITETURAIS

Qual ferramenta resolve qual problema?

ProblemaFerramenta
Não permitir duas linhas de pagamento para o mesmo pedidoUNIQUE + ON CONFLICT
Coordenar atualização de uma linha existenteSELECT ... FOR UPDATE / atomic update
Serializar uma chave lógica quando uma linha pode nem existirpg_advisory_xact_lock, quando realmente necessário
Múltiplos workers buscando trabalhos diferentesFOR UPDATE SKIP LOCKED
Evitar duplicar efeito em gateway externoIdempotency-Key no sistema externo + estado interno adequado
DB confirmou mas evento pode se perderTransactional Outbox
Regra: não usar lock como resposta genérica. Primeiro constraint/operação atômica; lock explícito só quando precisamos serializar execução lógica que a invariante do banco não resolve sozinha.
