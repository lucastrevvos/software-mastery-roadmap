ETAPA 1 · NESTJS

Criando os serviços

mkdir distributed-workshopCria o laboratório.
npx @nestjs/cli new orders-service --package-manager npm --skip-gitCria Orders sem Git interno.
npx @nestjs/cli new payments-service --package-manager npm --skip-gitCria Payments.

Decisões: @nestjs/observe = não por enquanto; ESM para usar import/export; Vitest veio junto com a opção ESM.

CLI: ng é normalmente Angular CLI. No Nest usamos nest ou npx @nestjs/cli.

ETAPA 2 · DOCKER

Um container para cada serviço

Docker Compose
├── orders
│   └── NestJS :3000
└── payments
    └── NestJS :3000

No Compose usamos:

build:
  context: ./orders-service
Descoberta #2 — build context: essa pasta vira a raiz disponível para o build. Portanto COPY . . no Dockerfile copia a partir de orders-service.
Descoberta #3 — localhost: dentro de Orders, localhost é o próprio container Orders. Para acessar Payments na rede do Compose usamos http://payments:3000.
No host:
localhost:3000 → orders:3000
localhost:3001 → payments:3000

Entre containers:
orders → http://payments:3000 → payments
Trade-off: Docker adiciona configuração, mas entrega isolamento, reprodução do ambiente e uma rede explícita sem a complexidade de Kubernetes.

ETAPA 3 · HTTP SÍNCRONO

Orders chama Payments e espera

POST /orders
   ↓
Orders cria orderId
   ↓
POST /payments
   ↓
Payments responde APPROVED
   ↓
Orders responde ao cliente
curl -X POST http://localhost:3000/orders -H "Content-Type: application/json" -d '{"amount":100}'Happy path executado com sucesso.
Descoberta #4 — dependência temporal: Orders precisa que Payments esteja disponível naquele momento para concluir a requisição.
HTTP síncrono: simples e com resposta imediata; em troca, disponibilidade e latência de Payments afetam Orders.

ETAPA 4 · FAILURE LAB

Desligamos Payments

docker compose stop paymentsSimula a dependência indisponível.
curl -X POST http://localhost:3000/orders -H "Content-Type: application/json" -d '{"amount":100}'Repete a chamada.

Primeiro resultado observado:

{"statusCode":500,"message":"Internal server error"}
Descoberta #5: Orders continuou no ar, mas a operação falhou porque Payments estava fora. Sem tratamento da falha remota, o cliente recebia um 500 genérico.

ETAPA 5 · DEBUG DO CONTAINER

Confirmando o código que realmente estava rodando

docker compose exec orders sed -n '1,220p' src/app.controller.tsInspeciona o arquivo dentro do container.
docker compose up -d --build --no-deps ordersRebuilda Orders sem subir Payments por causa do depends_on.
docker compose psConfirma quais serviços estão de fato rodando.
Descoberta #6 — imagem ≠ arquivos do host: sem volume, alterações locais só entram no container após novo build.
Descoberta #7 — depends_on: docker compose up ... orders pode iniciar Payments também. --no-deps evita subir dependências quando queremos isolar o experimento.
Erro encontrado: o bloco escrito como catch(error: unknown) { ... } havia ficado fora de um try. Nesse local, TypeScript o tratou como um método da classe chamado catch, portanto ele não capturava a exceção do fetch.
TypeScript: usamos unknown no catch porque qualquer valor pode ser lançado em JavaScript; antes de acessar propriedades, fazemos narrowing com error instanceof Error.

ETAPA 6 · TIMEOUT

Limitando quanto tempo Orders aceita esperar

signal: AbortSignal.timeout(2000)

Com Payments parado e apenas Orders em execução:

docker compose ps
→ apenas orders: Up

POST /orders
→ {"message":"Payment service timeout","error":"Gateway Timeout","statusCode":504}
Descoberta #8: no nosso ambiente, Payments parado não apareceu como erro imediato de conexão; a tentativa permaneceu pendente até o limite de 2 segundos e terminou em timeout.
Modelo mental importante: do ponto de vista de Orders, “serviço caiu” e “serviço está lento/rede não respondeu” podem ser indistinguíveis. O chamador só sabe que não recebeu resposta dentro do prazo.
Timeout: impede que uma dependência lenta prenda recursos indefinidamente. O custo é escolher um limite: curto demais gera falsos erros; longo demais propaga lentidão.
