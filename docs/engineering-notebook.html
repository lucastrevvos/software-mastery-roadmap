DIA 7

Arquivos, bytes e file descriptors

Hoje abandonei temporariamente fopen() e fui para a interface mais próxima do kernel: open(), read(), write() e close().

#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>

int main(void) {
    int fd = open("origem.txt", O_RDONLY);
    if (fd == -1) {
        perror("open");
        return 1;
    }

    char buffer[16];
    ssize_t n;

    while ((n = read(fd, buffer, sizeof buffer)) > 0) {
        if (write(STDOUT_FILENO, buffer, n) == -1) {
            perror("write");
            close(fd);
            return 1;
        }
    }

    if (n == -1) perror("read");
    close(fd);
    return 0;
}

Descoberta #22: open() não retorna “o arquivo”; retorna um inteiro que identifica uma entrada na tabela de descritores do processo.

0 = stdin
1 = stdout
2 = stderr
3 = primeiro descritor novo disponível

Ao observar /proc/PID/fd, vi algo como:

0 -> /dev/pts/0
1 -> /dev/pts/0
2 -> /dev/pts/0
3 -> /home/adrian/lab/origem.txt

Descoberta #23: o número do descritor é local ao processo. O descritor 3 de um processo não significa globalmente o mesmo objeto que o 3 de outro.

PROCESSO
  tabela de descritores
  0 -> stdin
  1 -> stdout
  2 -> stderr
  3 -> arquivo aberto
          |
          v
        KERNEL
          |
          +-- offset atual
          +-- flags
          +-- referência ao objeto do filesystem

Descoberta #24: uma abertura possui estado. Leituras sucessivas normalmente avançam o offset. lseek() pode reposicioná-lo quando o objeto suporta seek.

Também corrigi uma suposição: read(fd, buffer, 16) pede até 16 bytes. O retorno informa quantos bytes foram realmente entregues; 0 representa EOF em arquivo regular e -1 indica erro.

Descoberta #25: valores de retorno de syscalls fazem parte do contrato. Em programação de sistemas, ignorá-los significa jogar fora informação essencial.

Observei a execução com:

strace -e openat,read,write,close ./file_lab

Rastreamento simulado:

openat(..., "origem.txt", O_RDONLY) = 3
read(3, "hello\n", 16)             = 6
write(1, "hello\n", 6)             = 6
read(3, "", 16)                    = 0
close(3)                            = 0

Descoberta #26: strace deixa visível a conversa do processo com o kernel: qual descritor foi usado e quantos bytes atravessaram a fronteira.

DIA 8

Buffering: por que printf não chama write a cada caractere

Comparei escrita direta com write() e escrita pela biblioteca C usando printf()/fwrite(). A descoberta central foi separar duas camadas: a interface de alto nível da libc e as syscalls que atravessam a fronteira para o kernel.

#include <stdio.h>
#include <unistd.h>

int main(void) {
    for (int i = 0; i < 5; i++) {
        printf("X");
    }
    return 0;
}

Com strace -e write ./buffer_lab, em uma execução simulada apareceu apenas uma chamada de escrita ao final:

write(1, "XXXXX", 5) = 5

Descoberta #27: printf() normalmente escreve primeiro em um buffer mantido em user space. A libc acumula dados e decide quando chamar write().

Troquei para escrita direta:

for (int i = 0; i < 5; i++) {
    write(STDOUT_FILENO, "X", 1);
}

Agora o rastreamento mostrou cinco travessias:

write(1, "X", 1) = 1
write(1, "X", 1) = 1
write(1, "X", 1) = 1
write(1, "X", 1) = 1
write(1, "X", 1) = 1

Descoberta #28: syscall tem custo maior que uma simples operação em memória, porque envolve transição entre user space e kernel, validação de argumentos e trabalho do subsistema de I/O. Buffering reduz a frequência dessas travessias.

stdout muda de comportamento

Quando stdout estava ligado ao terminal, observei que uma quebra de linha frequentemente fazia o conteúdo aparecer logo. Ao redirecionar para arquivo, o comportamento mudou:

./buffer_lab > saida.txt

Isso me levou aos três modos conceituais de buffering da stdio:

unbuffered     -> tenta entregar imediatamente
line-buffered  -> tende a flushar em quebra de linha
fully-buffered -> acumula até encher/flush/fechamento

Descoberta #29: o comportamento de stdout pode depender do destino. Terminal e arquivo redirecionado não precisam usar a mesma estratégia de buffering.

Flush

Criei:

printf("carregando...");
sleep(3);
printf("ok\n");

Em determinada execução, carregando... demorou a aparecer. Forçando:

printf("carregando...");
fflush(stdout);
sleep(3);

o texto apareceu imediatamente.

Descoberta #30: existir no buffer da libc não significa que os bytes já chegaram ao kernel ou ao destino. fflush() força a biblioteca a entregar seu buffer ao próximo nível; ainda assim, isso não equivale automaticamente a garantir persistência física em disco.

stdio e descritor são camadas diferentes

fopen() retorna um FILE *, não um file descriptor puro. A biblioteca mantém estado adicional, como buffering e flags. Posso observar a ligação usando fileno().

FILE *f = fopen("dados.txt", "r");
printf("fd = %d\n", fileno(f));
fclose(f);

Descoberta #31: FILE * é uma abstração da biblioteca C sobre I/O; por baixo dela há, em sistemas POSIX, um descritor associado ao recurso aberto.

Experimento de custo

Comparei conceitualmente duas estratégias para escrever muitos bytes:

A) 1.000.000 chamadas write(..., 1)
B) buffers de 8192 bytes + poucas chamadas write()

A segunda reduz drasticamente o número de entradas no kernel. O ponto não é decorar “8192”; é entender o princípio: agrupar trabalho costuma ser mais eficiente do que atravessar a fronteira para cada byte.

Correção: “menos syscalls = sempre mais rápido” é uma heurística, não uma lei universal. Latência, interatividade, tamanho do buffer, dispositivo, cache e semântica da aplicação também importam.

DIA 9

Pipes, fork e processos conversando

Investiguei o que o shell monta ao executar cat arquivo.txt | grep erro. A peça central é pipe(), que cria dois descritores: uma ponta de leitura e uma ponta de escrita.

int fds[2];
pipe(fds);

fds[0] = leitura
fds[1] = escrita

Descoberta #33: pipe é um canal de bytes mantido pelo kernel. Um processo escreve em uma ponta e outro lê da outra; não há arquivo temporário no meio.

Em seguida usei fork(). O processo filho nasceu com cópias dos descritores abertos do pai. Esses descritores podem apontar para as mesmas estruturas abertas no kernel.

Descoberta #34: após fork(), pai e filho têm espaços de endereçamento virtuais separados, mas podem herdar referências para os mesmos recursos do kernel, incluindo pipes e arquivos abertos.

Montei uma comunicação simples:

int fds[2];
pipe(fds);

pid_t pid = fork();

if (pid == 0) {
    close(fds[1]);

    char buf[64];
    ssize_t n = read(fds[0], buf, sizeof buf);
    write(STDOUT_FILENO, buf, n);

    close(fds[0]);
} else {
    close(fds[0]);

    write(fds[1], "ola do pai\n", 11);
    close(fds[1]);

    wait(NULL);
}

Descoberta #35: fechar pontas não usadas é parte da semântica do pipe. Se algum processo ainda mantiver a ponta de escrita aberta, o leitor pode continuar esperando em vez de receber EOF.

Como o shell implementa |

shell
  |
  +-- pipe()
  |
  +-- fork() -> filho A
  |      dup2(pipe_write, STDOUT_FILENO)
  |      exec(cat ...)
  |
  +-- fork() -> filho B
         dup2(pipe_read, STDIN_FILENO)
         exec(grep ...)

dup2() permite fazer um descritor existente assumir o número 0 ou 1. Assim, os programas não precisam saber que estão ligados a um pipe: cat continua escrevendo em stdout e grep continua lendo de stdin.

Descoberta #36: redirecionamento no Unix funciona em grande parte porque programas usam stdin/stdout de forma abstrata, enquanto o shell rearranja os descritores antes de executar o programa.

EOF e bloqueio

Quando o buffer do pipe está vazio, read() pode bloquear esperando dados. Quando todas as pontas de escrita são fechadas, uma leitura que já consumiu os bytes pendentes retorna 0: EOF.

Descoberta #37: EOF em pipe não significa “não há bytes neste instante”; significa que não existem mais escritores capazes de produzir novos bytes naquele canal.

DIA 10

fork() cria; exec() substitui

Separei duas operações que o shell costuma combinar. fork() cria um novo processo; a família exec* substitui a imagem de programa do processo atual por outro executável.

pid_t pid = fork();

if (pid == 0) {
    execlp("ls", "ls", "-l", NULL);
    perror("execlp");
    _exit(127);
}

waitpid(pid, NULL, 0);

Descoberta #38: exec() bem-sucedido não cria outro PID e não retorna para o código antigo. O mesmo processo passa a executar outro programa.

antes:
PID 5201 -> meu_shellzinho

fork()
├─ PID 5201 -> pai
└─ PID 5202 -> filho

exec("ls") no filho:
PID 5202 -> ls

Descoberta #39: a identidade do processo no kernel sobrevive ao exec: PID, diretório atual e vários recursos continuam; a imagem de memória do programa é substituída e uma nova stack é preparada com argumentos e ambiente.

Observei com:

strace -f -e clone,fork,vfork,execve,wait4 ./launcher

Rastreamento conceitual:

clone(...)             = 5202
[pid 5202] execve("/usr/bin/ls", ["ls","-l"], ...) = 0
[pid 5201] wait4(5202, ...) = 5202

Descritores atravessando exec

Um descritor aberto antes do exec() normalmente continua aberto depois, a menos que esteja marcado close-on-exec (FD_CLOEXEC). Isso explica como o shell consegue preparar stdin/stdout/pipes antes e só depois carregar cat, grep ou outro programa.

Descoberta #40: redirecionamento funciona porque o shell monta o ambiente do processo primeiro e chama exec() depois. O programa novo já nasce vendo os descritores rearranjados.

Cagada do dia — buffer duplicado após fork

printf("antes");
fork();
return 0;

Se "antes" ainda estiver apenas no buffer da stdio quando ocorre o fork, pai e filho recebem cópias desse buffer em user space. Ao terminarem normalmente, ambos podem flushar a cópia e a saída aparecer duas vezes.

Descoberta #41: fork() copia o estado do processo visível em user space, inclusive buffers da biblioteca. fflush() antes do fork, ou usar escrita não-bufferizada quando apropriado, evita confundir “dados já enviados” com “dados ainda guardados na memória do processo”.

DIA 11

exit status, wait, zombies e orphans

Investiguei o fim do ciclo de vida de um processo. Um filho pode terminar a execução, liberar quase todos os recursos e ainda deixar uma pequena entrada no kernel contendo PID e informação de término até que o pai faça wait() ou waitpid().

pid_t pid = fork();

if (pid == 0) {
    _exit(42);
}

int status;
waitpid(pid, &status, 0);

if (WIFEXITED(status)) {
    printf("exit=%d\n", WEXITSTATUS(status));
}

Descoberta #42: terminar execução e ser completamente coletado são etapas diferentes. O status do filho precisa permanecer disponível para o pai.

Zumbi deliberado

if (fork() == 0) {
    _exit(0);
}

sleep(30); /* pai não chama wait ainda */

Durante a espera, ps -o pid,ppid,state,stat,cmd mostrou o filho como Z/<defunct>.

Descoberta #43: zombie não está executando e não mantém seu antigo heap/stack como um processo normal; é essencialmente um registro de término aguardando coleta pelo pai. Muitos zombies acumulados indicam falha de gerenciamento de processos.

Depois de waitpid(), a entrada desapareceu.

Exit status

No shell, um programa que faz return 42; em main produz um status observável com echo $?. Em C, o pai não deve interpretar o inteiro bruto de waitpid() diretamente; usa macros como WIFEXITED, WEXITSTATUS, WIFSIGNALED e WTERMSIG.

Descoberta #44: o término é um protocolo: um processo pode terminar normalmente com código de saída ou ser encerrado por sinal, e o pai consegue distinguir essas situações.

Quando o pai morre primeiro

Criei um filho que dormia enquanto o pai terminava. O filho continuou vivo. Seu PPID mudou porque o kernel o reparentou para um processo responsável por adotar/recolher órfãos — frequentemente PID 1, embora subreapers e namespaces possam mudar quem assume esse papel.

Descoberta #45: orphan e zombie são conceitos diferentes. Orphan é um processo vivo cujo pai terminou; zombie é um processo já terminado aguardando coleta.

Sinais entram no modelo

O comando kill PID envia SIGTERM por padrão. Ele pede uma terminação que o processo pode tratar ou ignorar. Já SIGKILL não pode ser capturado, ignorado ou tratado pelo processo.

kill PID
kill -TERM PID
kill -KILL PID

Quando um filho muda de estado/termina, o pai pode receber SIGCHLD; programas servidores costumam combinar esse mecanismo com waitpid() para reaproveitar filhos.

Descoberta #46: sinais são notificações assíncronas entregues pelo sistema operacional; não são chamadas de função normais entre processos.

DIA 12

Sinais, handlers e syscalls interrompidas

Instalei handlers com sigaction() e descobri que um sinal pode chegar de forma assíncrona enquanto o processo está executando outra coisa ou bloqueado numa syscall.

#include <signal.h>
#include <errno.h>
#include <unistd.h>

static volatile sig_atomic_t parar = 0;

static void on_signal(int signo) {
    (void) signo;
    parar = 1;
}

int main(void) {
    struct sigaction sa = {0};
    sa.sa_handler = on_signal;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;

    sigaction(SIGINT, &sa, NULL);
    sigaction(SIGTERM, &sa, NULL);

    char buf[128];

    while (!parar) {
        ssize_t n = read(STDIN_FILENO, buf, sizeof buf);

        if (n == -1) {
            if (errno == EINTR)
                continue;
            break;
        }

        if (n == 0)
            break;

        write(STDOUT_FILENO, buf, n);
    }

    return 0;
}

Descoberta #47: handler de sinal pode interromper o fluxo normal em um ponto imprevisível. Por isso ele deve fazer o mínimo possível.

Cagada do dia: printf dentro do handler

Minha primeira versão chamava printf() no handler. Corrigi: muitas funções da libc não são async-signal-safe; podem estar manipulando estado interno justamente quando o sinal chega. Para comunicação simples com o fluxo principal, usei um volatile sig_atomic_t.

Descoberta #48: código executado em contexto de sinal tem regras mais restritas que código comum. O padrão seguro é frequentemente registrar um estado mínimo no handler e deixar o fluxo normal realizar a limpeza.

read() pode voltar antes de receber dados

Com o processo bloqueado em read(), enviei SIGINT. Sem reinício automático daquela chamada, o retorno observado foi -1 com errno == EINTR.

read(...)
    |
    | processo dorme esperando I/O
    |
SIGINT chega
    |
handler executa
    |
read() pode retornar -1 / EINTR

Descoberta #49: erro não significa sempre “operação falhou definitivamente”. EINTR significa que a syscall foi interrompida por um sinal antes de completar; o programa precisa decidir se repete, encerra ou toma outra ação.

SA_RESTART

Ao usar sa.sa_flags = SA_RESTART, várias syscalls bloqueantes podem ser reiniciadas automaticamente depois do handler. Isso não vale universalmente para toda syscall/situação, então ainda preciso entender o contrato de cada operação.

Descoberta #50: sinais e I/O se cruzam. Um servidor robusto não pode assumir que toda syscall bloqueante só retorna por sucesso, EOF ou erro permanente.

Encerramento gracioso

O modelo que quero levar para servidores é:

SIGTERM
   |
   v
handler: parar = 1
   |
   v
fluxo principal percebe
   |
   +-- para de aceitar trabalho novo
   +-- termina trabalho em andamento
   +-- fecha descritores
   +-- libera recursos
   +-- exit

Isso é diferente de SIGKILL, no qual o processo não ganha oportunidade de executar handler nem sua lógica de shutdown.

Observação com strace

strace -e trace=read,write,rt_sigaction,rt_sigreturn ./signal_lab

O rastreamento permite ver a instalação do handler, a syscall bloqueante, a entrega do sinal e o retorno ao fluxo do processo.

Modelo mental: sinal = evento assíncrono entregue ao processo; handler = reação curta e restrita; fluxo principal = lugar para executar trabalho complexo e cleanup. Syscalls bloqueantes podem interagir com sinais através de EINTR ou reinício automático.

DIA 13

Primeiro socket: IP, porta e endpoint

Criei meu primeiro socket TCP IPv4 com socket(AF_INET, SOCK_STREAM, 0). O retorno foi apenas um inteiro, como nos arquivos e pipes: outro file descriptor apontando para um objeto mantido pelo kernel.

#include <arpa/inet.h>
#include <netinet/in.h>
#include <stdio.h>
#include <sys/socket.h>
#include <unistd.h>

int main(void) {
    int fd = socket(AF_INET, SOCK_STREAM, 0);
    if (fd == -1) {
        perror("socket");
        return 1;
    }

    struct sockaddr_in addr = {0};
    addr.sin_family = AF_INET;
    addr.sin_port = htons(8080);

    if (inet_pton(AF_INET, "127.0.0.1", &addr.sin_addr) != 1) {
        perror("inet_pton");
        close(fd);
        return 1;
    }

    if (bind(fd, (struct sockaddr *)&addr, sizeof addr) == -1) {
        perror("bind");
        close(fd);
        return 1;
    }

    if (listen(fd, 8) == -1) {
        perror("listen");
        close(fd);
        return 1;
    }

    printf("PID=%d fd=%d escutando em 127.0.0.1:8080\n",
           getpid(), fd);

    sleep(30);
    close(fd);
    return 0;
}

Descoberta #51: socket() cria um objeto de socket no kernel e devolve um descritor local ao processo. Nesse momento ele ainda não representa automaticamente uma conexão com alguém.

bind(): dar um endereço local ao socket

bind() associou o socket ao endereço local 127.0.0.1:8080. O IP identifica a interface/endereço local escolhido; a porta identifica um endpoint de transporte dentro daquela máquina.

127.0.0.1 : 8080
    IP       porta

127.0.0.1 é loopback: tráfego destinado a ele permanece na própria máquina. Isso é ótimo para laboratório porque não expõe o serviço para a rede externa.

Descoberta #52: porta não é “a aplicação”. Um processo pode possuir vários sockets/portas, e o kernel usa endereços e estado de transporte para encaminhar os bytes ao socket correto.

Por que htons(8080)?

O campo de porta no protocolo usa ordem de bytes de rede. htons() converte um inteiro de 16 bits da ordem do host para network byte order. Não devo gravar o número cru e assumir que toda arquitetura representa bytes da mesma forma.

Descoberta #53: protocolos precisam de uma representação compartilhada entre máquinas; network byte order evita que endianness local vire parte acidental do protocolo.

listen(): agora o socket é passivo

listen(fd, 8) não aceita cliente ainda. Ele coloca o socket TCP em modo de escuta e informa ao kernel que conexões de entrada podem ser enfileiradas até serem tratadas pela aplicação. O valor de backlog é uma solicitação sujeita às regras e limites do sistema.

Descoberta #54: socket de escuta e socket de conexão não são a mesma coisa. O descritor que fica em LISTEN será usado para produzir novos sockets conectados quando eu chegar em accept().

Observando o kernel

ls -l /proc/PID/fd
3 -> socket:[123456]

ss -ltnp
LISTEN 0 8 127.0.0.1:8080 0.0.0.0:* users:(("first_socket",pid=...,fd=3))

O arquivo em /proc/PID/fd/3 não aponta para um caminho no disco; mostra uma referência ao socket. Já ss revela o estado de rede que o kernel mantém.

strace

strace -e socket,bind,listen,close ./first_socket

Rastreamento conceitual:

socket(AF_INET, SOCK_STREAM, IPPROTO_IP) = 3
bind(3, {AF_INET, port=htons(8080), addr=127.0.0.1}, ...) = 0
listen(3, 8) = 0
close(3) = 0

Descoberta #55: a API de sockets encaixa no mesmo modelo de I/O que já construí: processo → file descriptor → objeto do kernel. A novidade é que esse objeto participa da pilha de rede.

Modelo mental

   |

dados da aplicação
