LEVEL 1 · DIA 1

Do código-fonte ao sistema operacional

Comecei com um programa mínimo em C e me recusei a aceitar printf() como magia. Compilei, inspecionei o executável e observei as chamadas feitas ao kernel.

#include <stdio.h>
int main(void){
    printf("Hello, world!\n");
    return 0;
}
gcc hello.c -o helloCompila C e gera um executável.
./helloExecuta o programa local.
file helloInspeciona formato do executável.
strace ./helloObserva system calls.
strace -e write ./helloFiltra chamadas write.
./hello > teste.txtRedireciona stdout.
cat teste.txtLê o arquivo.
Descoberta #1: printf() não conversa diretamente com a tela; a biblioteca C eventualmente pede ao kernel uma escrita observável como write(1,...).
Descoberta #2: stdout é um fluxo, não sinônimo de monitor.
código-fonte → compilador → executável → processo → biblioteca C → system call → kernel
LEVEL 1 · DIA 2

Programa ≠ processo

Fiz um programa permanecer vivo, imprimi seu PID e interroguei o processo pelo Linux.

#include <stdio.h>
#include <unistd.h>
int main(void){
    printf("Meu PID é %d\n", getpid());
    while(1) sleep(1);
}
psLista processos.
ls /proc/<PID>Explora a visão do processo exposta pelo procfs.
cat /proc/<PID>/statusMostra PID, PPID, estado, memória e threads.
kill <PID>Envia sinal ao processo.
ls -l /proc/<PID>/fdMostra file descriptors.
rm processRemove o executável do diretório.
Descoberta #3: PID identifica uma instância em execução.
Descoberta #4: PPID revelou o shell como pai do processo iniciado por ele.
Descoberta #5: apagar o executável no disco não tornou o processo vivo a mesma coisa que o arquivo apagado; programa e processo são entidades distintas.
PROCESSO ├── PID / PPID ├── memória ├── código em execução ├── file descriptors ├── estado └── threads
LEVEL 1 · DIA 3

Scheduler, concorrência e context switch

Forcei processos CPU-bound a competir pelo mesmo core para observar como poucas CPUs sustentam muitas tarefas.

int main(void){ while(1){} }
nprocMostra CPUs disponíveis.
ps -e --no-headers | wc -lConta processos listados.
topObserva uso de CPU.
./cpu_hog &Executa em background.
taskset -c 0 ./cpu_hogPrende a tarefa a uma CPU lógica.
pidstat -w 1Observa trocas de contexto.
nice -n 10 ./cpu_hogAltera o valor de nice.
Descoberta #6: muitos processos vivos não significam muitos processos fisicamente executando ao mesmo tempo.
Descoberta #7: dois processos CPU-bound presos ao mesmo core dividem tempo de CPU.
Descoberta #8: um processo pode estar vivo e praticamente não usar CPU porque está dormindo ou esperando I/O.
Descoberta #9: context switch preserva estado suficiente de uma execução e restaura o estado de outra.
Correção: não existe um único intervalo universal em que todo processo obrigatoriamente é trocado; scheduling depende de política, prioridade, carga, bloqueios e CPUs disponíveis.
READY → RUNNING → WAITING → READY Ready = quer CPU Running = executa agora Waiting = aguarda algo
LEVEL 1 · DIA 4

Cada processo vive em seu próprio espaço de endereçamento

Minha pergunta era: se eu iniciar duas cópias do mesmo programa, uma variável global de uma execução é a mesma variável da outra? Fiz duas instâncias manterem e alterarem seu próprio contador.

#include <stdio.h>
#include <unistd.h>

int contador = 10;

int main(void){
    printf("PID=%d contador=%d endereco=%p\n", getpid(), contador, (void*)&contador);
    contador += 100;
    printf("PID=%d contador=%d\n", getpid(), contador);
    sleep(30);
    return 0;
}

Executei duas cópias. Ambas começaram com contador = 10 e ambas chegaram a 110 independentemente. Alterar a variável de uma execução não alterou a da outra.

./memory &Inicia uma instância em background; repeti para criar dois processos.
ps -C memory -o pid,cmdLista os PIDs das instâncias do programa.
cat /proc/<PID>/mapsMostra regiões do espaço de endereçamento virtual do processo.
pmap <PID>Exibe um mapa resumido das regiões de memória do processo.
Descoberta #10: duas instâncias do mesmo executável têm, por padrão, estados de memória isolados. Alterar uma variável em um processo não altera automaticamente a variável do outro.
Descoberta #11: os endereços usados pelo programa pertencem a um espaço de endereçamento virtual. O processo não manipula RAM física diretamente como se enxergasse toda a máquina.
Descoberta #12: /proc/PID/maps revelou várias regiões: código do executável, bibliotecas, heap, stack e outros mapeamentos.
Correção importante: “processos têm memória isolada” não significa que nenhum byte físico possa ser compartilhado. O sistema operacional pode compartilhar páginas de código, bibliotecas, arquivos mapeados ou memória explicitamente compartilhada. A abstração normal é que cada processo possui seu próprio espaço de endereçamento virtual protegido.

Modelo mental

Processo A Processo B endereço virtual 0x... endereço virtual 0x... │ │ └──── tabelas de páginas ──────────┘ ↓ memória física Cada processo enxerga seu próprio mapa virtual. O kernel/MMU controla como esse mapa chega à memória física.
Checkpoint: processo não é apenas “código usando CPU”; ele executa dentro de um espaço de endereçamento virtual que ajuda a dar isolamento, proteção e flexibilidade ao sistema operacional.
