LEVEL 1 · DIA 1

Do código-fonte ao sistema operacional

Comecei com um programa mínimo em C e me recusei a aceitar printf() como magia. Compilei, inspecionei o executável e observei as chamadas feitas ao kernel.

Experimento inicial

#include <stdio.h>

int main(void)
{
    printf("Hello, world!\n");
    return 0;
}
gcc hello.c -o helloCompila o arquivo C e gera um executável.
./helloExecuta o programa presente no diretório atual.
lsLista arquivos do diretório; usei para confirmar a criação do executável.
file helloInspeciona o tipo do arquivo; revelou ELF, x86-64 e linking dinâmico.
strace ./helloMostra system calls realizadas pelo processo.
strace -e write ./helloFiltra o rastreamento para observar apenas chamadas write.
./hello > teste.txtRedireciona stdout para um arquivo.
cat teste.txtLê o conteúdo do arquivo no terminal.
Descoberta #1: printf() não conversa diretamente com a tela. A biblioteca C acaba pedindo ao sistema operacional uma operação de escrita, observável como write(1, ...).
Descoberta #2: stdout não significa “monitor”. É um fluxo. O shell pode conectá-lo ao terminal, a um arquivo ou a outro destino.

Descritores padrão

0 = stdin
1 = stdout
2 = stderr

Modelo mental

hello.c ↓ compilador ↓ executável ↓ sistema operacional carrega ↓ processo ↓ biblioteca C → system call → kernel → destino
Checkpoint: programa e código-fonte não são a mesma coisa; o arquivo .c é texto, o executável é outra representação, e o processo é a execução acontecendo.
LEVEL 1 · DIA 2

Programa ≠ processo

Eu precisava enxergar um processo vivo. Fiz um programa permanecer em execução, imprimi seu PID e comecei a interrogá-lo pelo Linux.

#include <stdio.h>
#include <unistd.h>

int main(void)
{
    printf("Meu PID é %d\n", getpid());
    while (1) sleep(1);
    return 0;
}
psLista processos associados ao terminal atual.
ls /proc/<PID>Explora a representação virtual que o Linux expõe para um processo.
cat /proc/<PID>/statusExibe PID, PPID, estado, memória, threads e outras informações.
kill <PID>Envia um sinal ao processo; usei para encerrá-lo externamente.
ls /proc/<PID>/fdLista os file descriptors abertos pelo processo.
ls -l /proc/<PID>/fdMostra para onde cada descritor aponta.
ps -p <PID>Consulta um processo específico.
rm processApaga o executável do diretório; usei para testar se o processo vivo sobreviveria.
Descoberta #3: PID é a identidade atribuída pelo sistema operacional a uma instância em execução. Duas execuções do mesmo executável podem ter PIDs diferentes.
Descoberta #4: PPID revelou que meu shell bash era o processo pai do programa iniciado a partir dele.
Descoberta #5: apagar o arquivo executável enquanto o processo estava vivo não interrompeu imediatamente aquele processo. Isso tornou concreta a diferença entre executável no disco e processo em execução.

Modelo mental

PROCESSO │ ├── PID / PPID ├── memória ├── código em execução ├── file descriptors ├── estado ├── usuário └── threads
Checkpoint: programa é uma descrição armazenada; processo é uma instância viva gerenciada pelo kernel.
LEVEL 1 · DIA 3

Scheduler, concorrência e context switch

Eu tinha centenas de processos e poucas CPUs lógicas. Então forcei processos CPU-bound a competir pelo mesmo core e observei o scheduler distribuindo tempo de execução.

int main(void)
{
    while (1) { }
    return 0;
}
nprocMostra a quantidade de unidades de processamento disponíveis ao sistema.
ps -e --no-headers | wc -lConta aproximadamente quantos processos estão listados.
topObserva processos e uso de CPU em tempo real.
./cpu_hog &Executa o processo em background no shell.
taskset -c 0 ./cpu_hogRestringe o processo à CPU lógica 0 para tornar a disputa observável.
pidstat -w 1Observa trocas de contexto voluntárias e involuntárias por processo.
nice -n 10 ./cpu_hogInicia um processo com valor de nice alterado, influenciando sua prioridade de CPU.
taskset -c 0 nice -n 10 ./cpu_hogCombina afinidade de CPU e nice para observar competição controlada.
Descoberta #6: centenas de processos “vivos” não significam centenas de processos fisicamente executando ao mesmo tempo. O scheduler escolhe quais tarefas recebem CPU.
Descoberta #7: quando dois processos CPU-bound foram presos ao mesmo core, cada um passou a receber aproximadamente uma fração do tempo disponível.
Descoberta #8: um processo pode estar vivo sem consumir CPU de forma relevante porque pode estar dormindo ou aguardando I/O.
Descoberta #9: uma troca de contexto envolve preservar o estado necessário de uma execução e restaurar o estado de outra para que cada uma continue de onde parou.
Correção importante: eu inicialmente simplifiquei demais dizendo que “cada processo recebe alguns milissegundos e obrigatoriamente ocorre uma troca”. O comportamento real depende do scheduler, prioridades, carga, bloqueios e CPUs disponíveis.

Estados — primeiro modelo

READY ↓ RUNNING ↓ WAITING ↓ READY Ready = quer CPU Running = está executando Waiting = aguarda algo; CPU não ajuda agora

Intuição nova

“Simultâneo” é uma palavra perigosa. Agora eu separo: estar vivo, estar pronto, estar esperando e estar efetivamente executando numa CPU.

Boss Fight: com 8 CPUs lógicas e 247 processos, apenas um conjunto limitado de threads pode executar fisicamente em cada instante. O sistema operacional agenda tarefas, interrompe, preserva estado e retoma execuções conforme sua política.
