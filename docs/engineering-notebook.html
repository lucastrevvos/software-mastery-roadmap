LEVEL 1 · DIA 1

Do código-fonte ao kernel

Compilei um Hello World, inspecionei o ELF e usei strace para descobrir que printf() termina em operações como write(). Aprendi que stdout é um fluxo, não “a tela”.

gcc hello.c -o helloCompilar C.
file helloInspecionar executável.
strace -e write ./helloObservar system calls de escrita.
./hello > teste.txtRedirecionar stdout.
Descobertas #1–2: bibliotecas escondem chamadas ao sistema; stdin/stdout/stderr são descritores e fluxos conectáveis.
LEVEL 1 · DIA 2

Programa ≠ processo

Observei PID, PPID, descritores e estado por /proc. Duas execuções do mesmo executável viraram dois processos distintos.

psListar processos.
cat /proc/PID/statusInspecionar estado.
ls -l /proc/PID/fdVer descritores.
kill PIDEnviar sinal.
Descobertas #3–5: processo é uma instância viva gerenciada pelo kernel; o executável no disco é outra entidade.
LEVEL 1 · DIA 3

Scheduler e context switch

Prendi processos CPU-bound ao mesmo core e observei que tarefas vivas não significam tarefas executando fisicamente ao mesmo tempo.

nprocConsultar CPUs.
topObservar CPU.
taskset -c 0 ./cpu_hogFixar afinidade.
pidstat -w 1Observar context switches.
nice -n 10 ./cpu_hogInfluenciar scheduling.
Descobertas #6–9: scheduler decide quem recebe CPU; waiting, ready e running são estados diferentes; context switch preserva e restaura estado de execução.
LEVEL 1 · DIA 4

Memória virtual e isolamento

Duas instâncias do mesmo programa alteraram suas variáveis independentemente. Com /proc/PID/maps e pmap, enxerguei o espaço de endereçamento virtual de cada processo.

cat /proc/PID/mapsVer regiões virtuais.
pmap PIDResumir mapeamentos.
Descobertas #10–12: ponteiros normalmente representam endereços virtuais no contexto de um processo; MMU e tabelas de páginas ligam esse espaço à memória física.
Correção: isolamento virtual não implica ausência total de páginas físicas compartilhadas.
LEVEL 1 · DIA 5

Stack, heap e malloc

Separei a variável ponteiro do bloco apontado, observei stack frames e usei strace para ver que malloc() trabalha através de um alocador, que pode recorrer a brk/mmap. Criei também meu primeiro memory leak.

gcc -O0 -g arquivo.c -o programaBuild pedagógica e de debug.
strace -e brk,mmap,munmap ./programaObservar obtenção/mapeamento de memória.
valgrind --leak-check=full ./programaDetectar leaks.
Descobertas #13–16: ponteiro e objeto apontado têm lifetimes distintos; stack acompanha chamadas; heap permite lifetime dinâmico; free() normalmente devolve um bloco ao alocador, não necessariamente ao kernel imediatamente.
LEVEL 1 · DIA 6

Quando um ponteiro continua existindo, mas o objeto não

Hoje eu quebrei memória de propósito. O objetivo foi separar três ideias: endereço existente, objeto ainda vivo e acesso permitido. Descobri que essas coisas não são equivalentes.

Experimento 1 — use-after-free

#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int *p = malloc(sizeof *p);
    if (!p) return 1;

    *p = 42;
    printf("antes do free: %d\n", *p);

    free(p);

    printf("depois do free: %d\n", *p); /* BUG */
    return 0;
}

Sem instrumentação, uma execução simulada chegou a imprimir 42 de novo. Em outra build poderia aparecer lixo ou o programa poderia falhar. A conclusão não é “funcionou”; a conclusão é que o programa fez algo que C não define.

Descoberta #17: free(p) encerra o direito do programa de usar aquele bloco através daquele ponteiro. O valor numérico do endereço pode continuar armazenado em p, mas o objeto alocado já terminou seu lifetime.
Correção importante: “se memória inválida for acessada, haverá segmentation fault” é falso. Muitos bugs de memória não falham imediatamente. O programa pode parecer correto e quebrar depois, em outra máquina ou com outra otimização.

AddressSanitizer entra no arsenal

gcc -O0 -g -fsanitize=address -fno-omit-frame-pointer uaf.c -o uafCompila instrumentando acessos de memória para detectar vários erros em runtime.
./uafExecuta a build instrumentada.

Resultado simulado resumido:

ERROR: AddressSanitizer: heap-use-after-free
READ of size 4
...
freed by thread T0 here:
    free
    main ... uaf.c

previously allocated by thread T0 here:
    malloc
    main ... uaf.c

Esse relatório é quase uma autópsia: onde usei, onde liberei e onde originalmente aloquei.

Experimento 2 — endereço de variável local

int *criar(void) {
    int x = 99;
    return &x; /* errado */
}

O compilador já me avisa que estou retornando o endereço de uma variável local. Quando a função retorna, o lifetime de x termina. O endereço numérico pode até permanecer em algum ponteiro, mas não existe mais um int x válido que eu possa continuar usando por esse endereço.

Descoberta #18: um ponteiro pode sobreviver ao objeto para o qual apontava. Esse ponteiro passa a ser um dangling pointer.

Experimento 3 — ultrapassar um buffer

int main(void) {
    int valores[3] = {10, 20, 30};

    valores[3] = 999; /* índice válido: 0..2 */

    return 0;
}

Eu estava acostumado a ler isso como “índice errado”. Agora penso em bytes: reservei espaço para três int contíguos e pedi ao processador que escrevesse além do objeto.

Com AddressSanitizer, o resultado simulado foi:

ERROR: AddressSanitizer: stack-buffer-overflow
WRITE of size 4
...
Descoberta #19: C não coloca automaticamente uma barreira lógica em volta de cada array a cada acesso. Escrever além do limite pode corromper outro dado existente naquela região de memória.

O conceito que une os três bugs

PONTEIRO / ENDEREÇO ≠ OBJETO VÁLIDO ≠ PERMISSÃO PARA ACESSAR malloc → objeto nasce free → lifetime termina função entra → locais automáticos ganham lifetime função sai → lifetime termina array[0..N-1] → região válida fora dela → acesso fora do objeto

Comportamento indefinido

Encontro um conceito central de C: undefined behavior. Quando o programa viola certas regras da linguagem — como ler memória depois de free() ou acessar um array fora de seus limites — o padrão da linguagem deixa de prometer qual será o resultado.

Isso explica por que um bug pode:

funcionar no debug
quebrar em release
funcionar hoje
quebrar depois de uma mudança inocente
imprimir o valor antigo
imprimir lixo
crashar
Descoberta #20: bugs de memória são perigosos justamente porque o sintoma pode aparecer longe da causa. O erro pode acontecer numa escrita e a falha só surgir quando outro código usa os bytes corrompidos.

Segundo instrumento: Valgrind

valgrind --track-origins=yes ./programaAjuda a localizar acessos inválidos e a origem de alguns valores problemáticos.

Para um use-after-free, espero mensagens no estilo:

Invalid read of size 4
Address ... is 0 bytes inside a block of size 4 free'd

Terceiro instrumento: GDB

Agora entro pela primeira vez num debugger de verdade:

gdb ./programaAbre o executável no GNU Debugger.
break mainCria um breakpoint em main.
runInicia o processo controlado pelo debugger.
nextAvança uma linha sem entrar na função chamada.
stepAvança entrando na função.
print pInspeciona o valor do ponteiro.
print *pTenta inspecionar o objeto apontado enquanto ele é válido.
btMostra a cadeia de chamadas (backtrace).

O debugger muda minha forma de trabalhar. Até aqui eu alterava código, colocava printf() e rodava novamente. Agora posso pausar uma execução viva e interrogá-la.

Descoberta #21: debugging não é adivinhação. Posso parar o processo, observar stack frames, variáveis, endereços e a cadeia de chamadas exatamente no ponto em que o comportamento se desvia.
Boss Fight: um ponteiro conter 0x1234... não prova que existe ali um objeto válido para mim. Antes de dereferenciar, existe uma pergunta mais fundamental: o objeto ainda está vivo, esse endereço pertence a ele e esse acesso está dentro de seus limites?
