LEVEL 1 · DIA 1

Do código-fonte ao kernel

Compilei um Hello World, inspecionei o ELF e usei strace para descobrir que printf() termina em operações como write(). Aprendi que stdout é um fluxo, não “a tela”.

gcc hello.c -o helloCompilar C.
file helloInspecionar executável.
strace -e write ./helloObservar system calls de escrita.
./hello > teste.txtRedirecionar stdout.
Descobertas #1–2: bibliotecas escondem chamadas ao sistema; stdin/stdout/stderr são descritores e fluxos conectáveis.
LEVEL 1 · DIA 2

Programa ≠ processo

Observei PID, PPID, descritores e estado por /proc. Duas execuções do mesmo executável viraram dois processos distintos.

psListar processos.
cat /proc/PID/statusInspecionar estado.
ls -l /proc/PID/fdVer descritores.
kill PIDEnviar sinal.
Descobertas #3–5: processo é uma instância viva gerenciada pelo kernel; o executável no disco é outra entidade.
LEVEL 1 · DIA 3

Scheduler e context switch

Prendi processos CPU-bound ao mesmo core e observei que tarefas vivas não significam tarefas executando fisicamente ao mesmo tempo.

nprocConsultar CPUs.
topObservar CPU.
taskset -c 0 ./cpu_hogFixar afinidade.
pidstat -w 1Observar context switches.
nice -n 10 ./cpu_hogInfluenciar scheduling.
Descobertas #6–9: scheduler decide quem recebe CPU; waiting, ready e running são estados diferentes; context switch preserva e restaura estado de execução.
LEVEL 1 · DIA 4

Memória virtual e isolamento

Duas instâncias do mesmo programa alteraram suas variáveis independentemente. Com /proc/PID/maps e pmap, enxerguei o espaço de endereçamento virtual de cada processo.

cat /proc/PID/mapsVer regiões virtuais.
pmap PIDResumir mapeamentos.
Descobertas #10–12: ponteiros normalmente representam endereços virtuais no contexto de um processo; MMU e tabelas de páginas ligam esse espaço à memória física.
Correção: isolamento virtual não implica ausência total de páginas físicas compartilhadas.
LEVEL 1 · DIA 5

Stack, heap e o que malloc realmente faz

Para observar sem o compilador esconder demais o fenômeno, compilei com -O0. Criei uma variável local e uma alocação dinâmica, imprimi seus endereços e comparei com /proc/PID/maps.

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

int global = 7;

void experimento(void) {
    int local = 42;
    int *dinamico = malloc(sizeof(int));
    if (dinamico == NULL) exit(1);
    *dinamico = 99;

    printf("global   %p = %d\n", (void*)&global, global);
    printf("local    %p = %d\n", (void*)&local, local);
    printf("ponteiro %p\n", (void*)&dinamico);
    printf("heap     %p = %d\n", (void*)dinamico, *dinamico);

    sleep(30);
    free(dinamico);
}

int main(void) {
    experimento();
    return 0;
}

Resultado simulado:

global   0x404040 = 7
local    0x7ffd6d54b8ac = 42
ponteiro 0x7ffd6d54b8a0
heap     0x1f7d2a0 = 99
Descoberta #13: a variável dinamico (o ponteiro) e o bloco para o qual ela aponta são coisas diferentes. O ponteiro local pode estar no frame da função enquanto os bytes obtidos por malloc() pertencem à memória dinâmica administrada pelo alocador.
Descoberta #14: stack está fortemente ligada a chamadas de função: frames carregam informações como locais, argumentos/temporários e estado necessário para retornar. Quando a função termina, seu frame deixa de estar válido. Isso explica o lifetime automático.
Descoberta #15: malloc(n) não significa “peça exatamente n bytes diretamente ao kernel”. Normalmente ele pede um bloco ao alocador da biblioteca; esse alocador reaproveita arenas/blocos e, quando precisa de mais memória virtual, pode recorrer a mecanismos do sistema como brk e/ou mmap. A estratégia é implementação-dependente.
Descoberta #16: free(ptr) devolve o bloco ao alocador para reutilização; isso não implica que a RAM correspondente seja imediatamente devolvida ao sistema operacional.

Experimento: observar o alocador conversando com o kernel

gcc -O0 -g memory_regions.c -o memory_regionsCompila sem otimização e inclui símbolos de debug.
strace -e brk,mmap,munmap ./memory_regionsObserva syscalls relacionadas a obtenção/mapeamento de memória virtual.
cat /proc/PID/mapsCompara endereços impressos com regiões como [heap] e [stack].
valgrind --leak-check=full ./memory_regionsDetecta vazamentos e vários usos inválidos de memória.

Um strace simplificado mostrou chamadas como:

brk(NULL) = 0x1f7b000
brk(0x1f9c000) = 0x1f9c000
mmap(NULL, 8192, PROT_READ|PROT_WRITE, ... ) = ...
Correção importante: “variável local fica na stack” é um bom modelo inicial, mas não uma lei da linguagem C. Otimizações podem manter valores apenas em registradores, eliminar variáveis ou reorganizar armazenamento. Estou usando -O0 para tornar o experimento pedagógico.

Primeiro bug deliberado: memory leak

void vazar(void) {
    int *p = malloc(1000);
    /* esqueci free(p); */
}

Ao repetir a função, continuo pedindo blocos ao alocador e perco a referência necessária para liberá-los. O processo pode acumular memória inutilizável até terminar.

STACK chamada de função ↓ frame ├── estado de retorno ├── locais / temporários (modelo inicial) └── termina junto com a chamada HEAP / memória dinâmica malloc() ↓ alocador da libc ↓ bloco com lifetime controlado pelo programa ↓ free() malloc/free ≠ syscall direta a cada chamada
Boss Fight: se uma função faz int *p = malloc(100), existem duas entidades: a variável ponteiro p e o bloco apontado. O lifetime de p segue o escopo/armazenamento da variável; o bloco alocado continua existindo até ser liberado (ou o processo terminar), mesmo que eu perca o ponteiro — e aí nasce um leak.

Ponteiros perigosos
