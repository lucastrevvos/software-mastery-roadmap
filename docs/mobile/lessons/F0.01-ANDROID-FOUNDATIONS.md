## 1. Modelo mental: app, sistema operacional e hardware

Um aplicativo mobile não controla o hardware diretamente como se fosse proprietário do telefone. Ele usa APIs providas pelo sistema. No Android, a arquitetura pode ser visualizada (simplificadamente):

    Aplicativo (Kotlin + UI + regras)
                ↓
    Android Framework / APIs
                ↓
    Android Runtime (ART) e bibliotecas nativas
                ↓
    HAL / Kernel Linux / Drivers
                ↓
    CPU, RAM, armazenamento, GPS, câmera, sensores

**Cuidado:** essa representação é pedagógica, não afirma que todas as chamadas percorrem linearmente todas as camadas.

- **Kernel Linux:** gerencia escalonamento, memória, processos e drivers.
- **Android Framework:** oferece APIs como Activity, notificações, permissões e acesso a serviços do sistema.
- **ART:** executa código Android gerenciado, incluindo bytecode gerado a partir de Kotlin/Java; possui mecanismos de compilação/otimização e gerenciamento de memória.
- **HAL:** abstrai interações específicas com hardware para serviços de sistema.
- **Aplicativo:** entrega comportamento de produto utilizando recursos permitidos pelo sistema.

**Exemplo KM One:** um recurso de localização usa APIs do Android; as permissões e as restrições de execução em segundo plano são mediadas pelo sistema. Não basta escrever uma função Kotlin que 'ligue o GPS'.

O Android normalmente atribui identidade Linux e processo isolados a cada app (**sandbox**). Outros apps não podem ler arbitrariamente seus dados privados.

Referência: [Android — Application fundamentals](https://developer.android.com/guide/components/fundamentals).

## 2. Aplicativo é diferente de processo e de tela

- **Aplicativo:** pacote de componentes, recursos e código instalados.
- **Processo:** instância de execução do código, criada e eventualmente encerrada pelo sistema.
- **Activity:** componente com lifecycle próprio; tradicionalmente representa um ponto de entrada de UI.
- **Tela/rota em Jetpack Compose:** parte da interface dentro de uma Activity; um app moderno pode usar uma **única Activity** para várias telas.
- **Task / back stack:** organiza a navegação de Activities; não é sinônimo de processo.

**Erro comum:** assumir que navegar da tela 'Ofertas' para 'Registros' significa destruir uma Activity. Em um app single-Activity com Compose Navigation, ambas podem ser destinos da mesma Activity.

O Android pode encerrar o **processo** de um app em background por pressão de memória. Ao retornar, o app precisa recuperar estado e dados relevantes.

Referência: [Android — App architecture](https://developer.android.com/topic/architecture).

## 3. Componentes fundamentais

| Componente | Para que serve | Exemplo |
|---|---|---|
| **Activity** | Interação com o usuário e ciclo de vida da UI | Activity principal do app |
| **Service** | Operação que não depende diretamente de interface visível; sujeita às regras de execução em background | Reprodução de mídia, operação contínua permitida |
| **BroadcastReceiver** | Reage a determinados eventos enviados por broadcast | Receber evento do sistema permitido |
| **ContentProvider** | Expõe/gerencia dados por interface padronizada e controlada | Compartilhar conteúdo com outro app |

O **Intent** é um mecanismo para solicitar ações e ativar alguns componentes; ele não concede automaticamente permissões.

Um **Service não significa thread separada** e também **não significa execução eterna**. Para trabalho persistente e adiado, estudar futuramente WorkManager; o componente correto depende do caso e das restrições atuais.

Referência: [Android — App components](https://developer.android.com/guide/components/fundamentals).

## 4. Ciclo de vida de uma Activity

O Android fornece seis callbacks principais: **onCreate, onStart, onResume, onPause, onStop e onDestroy**. Há também **onRestart** na volta de uma Activity parada.

### Abertura típica

    onCreate → onStart → onResume
    criada    visível     em primeiro plano e apta a interagir

### Ao pressionar Home (caso comum de Activity totalmente oculta)

    onPause → onStop

### Ao retornar sem recriação

    onRestart → onStart → onResume

### Encerramento normal da Activity

    onPause → onStop → onDestroy

**Esses são caminhos comuns, não promessa universal para toda situação.** Uma Activity pode ficar parcialmente visível e pausada; mudança de configuração pode recriá-la; o SO pode encerrar o processo sem chamar onDestroy.

| Callback | Ideia básica |
|---|---|
| **onCreate** | Inicialização de uma nova instância da Activity; configurar a interface |
| **onStart** | Activity torna-se visível |
| **onResume** | Activity chega ao estado resumed; recebe interação principal |
| **onPause** | Está perdendo o foco/entrando em estado pausado; operações breves |
| **onStop** | Não está mais visível |
| **onRestart** | Volta ao caminho de início a partir do estado stopped |
| **onDestroy** | Activity está sendo destruída em um encerramento/recriação normal; pode não ocorrer quando o processo é morto |

Não fazer gravações críticas somente em **onDestroy**. Para tarefas que dependem da Activity, respeitar o lifecycle e recursos consumidos.

### Código ilustrativo em Kotlin

Este trecho representa uma Activity que registra transições. Pode ser usado em um projeto Android com Activity configurada no Manifest, Android SDK e dependências apropriadas:

\`\`\`kotlin
import android.os.Bundle
import android.util.Log
import androidx.activity.ComponentActivity

class MainActivity : ComponentActivity() {
    private val tag = "LifecycleLab"

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        Log.d(tag, "onCreate")
    }

    override fun onStart() {
        super.onStart()
        Log.d(tag, "onStart")
    }

    override fun onResume() {
        super.onResume()
        Log.d(tag, "onResume")
    }

    override fun onPause() {
        Log.d(tag, "onPause")
        super.onPause()
    }

    override fun onStop() {
        Log.d(tag, "onStop")
        super.onStop()
    }

    override fun onRestart() {
        super.onRestart()
        Log.d(tag, "onRestart")
    }

    override fun onDestroy() {
        Log.d(tag, "onDestroy")
        super.onDestroy()
    }
}
\`\`\`

**Atenção:** no Compose, **recomposition não significa recriação da Activity**. O Compose pode redesenhar por alterações de estado enquanto a mesma Activity segue no estado Resumed.

Referência: [Android — Activity lifecycle](https://developer.android.com/guide/components/activities/activity-lifecycle).

## 5. Onde fica o estado?

Imagine que a pessoa digitou um valor em um formulário, mudou a orientação do celular e depois alternou de aplicativo:

- **Variável local / estado apenas em memória:** pode desaparecer na recriação.
- **ViewModel:** geralmente mantém estado da UI durante mudança de configuração, mas **não sobrevive à morte do processo**.
- **rememberSaveable / SavedStateHandle:** podem restaurar informações pequenas e apropriadas após recriação, inclusive alguns cenários de morte do processo iniciada pelo sistema, respeitadas as condições do sistema.
- **Banco local (ex.: Room) / DataStore:** persistência durável apropriada; o dado pode ser recuperado após o processo ser encerrado e o aplicativo reiniciado.
- **Backend:** fonte remota, quando fizer sentido, sujeito à conectividade.

**Regra de projeto:** não tratar memória RAM como armazenamento permanente e não presumir que onDestroy será chamado antes de uma morte de processo.

Referências: [Saving UI state](https://developer.android.com/topic/libraries/architecture/viewmodel/viewmodel-savedstate) · [Saving States](https://developer.android.com/topic/libraries/architecture/views/saving-states-views).

## 6. Exemplos guiados

### Cenário A — abrir e apertar Home
O usuário abre a Activity principal; o Android normalmente chama onCreate → onStart → onResume. Ao usar Home, a Activity tipicamente recebe onPause → onStop e permanece no processo caso ele ainda exista. Não confundir background com 'encerrado'.

### Cenário B — girar o dispositivo
Uma rotação pode causar mudança de configuração e recriar a Activity: onDestroy seguido por novo onCreate, com eventos intermediários. É importante separar estado que pode ser reconstituído de dados que precisam persistir. Isso depende da configuração e do comportamento do app.

### Cenário C — Android encerra processo parado
O app estava em background. Para recuperar memória, o SO encerra o processo. onDestroy **não é garantido**. Na reabertura, nova instância e processo podem ser criados. O app deve reconstruir a UI a partir do estado salvo ou persistido.

### Cenário D — Compose troca uma rota
Navegar entre dois destinos Compose pode acontecer **na mesma Activity**. A mudança de tela não exige necessariamente onDestroy/onCreate da Activity. Há lifecycle de destinos de navegação, além do lifecycle da Activity.
