POR QUE EMPRESAS ADOTAM NEXT.JS

Não é só “React com rotas”

Convençõesrouting, layouts, bundling e otimizações integradas reduzem decisões repetitivas.
Renderingpermite combinar renderização estática, dinâmica, streaming e componentes de servidor.
Menos JavaScriptServer Components permitem manter partes da árvore no servidor e mandar menos JS ao browser.
SEO e performanceHTML pode existir antes da execução de JavaScript no cliente.
Full-stack/BFFRoute Handlers e Server Actions permitem lógica server-side próxima da UI.
Padronização de equipeuma arquitetura comum para projetos React reduz variações entre times.

MODELO MENTAL

React x Next.js

React
  └─ biblioteca/modelo de componentes e UI

Next.js
  └─ framework em cima de React
      ├─ routing
      ├─ rendering no servidor
      ├─ Server Components
      ├─ cache/revalidation
      ├─ Route Handlers
      ├─ build/bundling
      └─ deployment/runtime conventions
Importante: Server Components e SSR não são sinônimos. Server Components definem onde um componente executa e quanto JS vai ao cliente; SSR descreve a geração de HTML no servidor. Podem trabalhar juntos.

SERVER x CLIENT COMPONENTS

A boundary que mais cai em Next moderno

Server Component (default no App Router)
├─ pode buscar DB/API no servidor
├─ pode usar secrets server-side
├─ reduz JS enviado ao browser
└─ não usa useState/useEffect/window/localStorage

Client Component ('use client')
├─ state
├─ event handlers
├─ effects
├─ browser APIs
└─ custom hooks client-side
Heurística: deixar a maior árvore possível no servidor e empurrar 'use client' para ilhas realmente interativas, em vez de transformar páginas inteiras em Client Components.

NEXT.JS + SISTEMAS DISTRIBUÍDOS

Eles se encontram na borda do sistema

Browser
   ↓
Next.js
   ├─ SSR / Server Components
   ├─ BFF / Route Handlers
   ├─ auth/session
   ├─ cache
   └─ agregação de dados
          ↓
   NestJS / APIs / microsserviços
      ├─ Orders
      ├─ Payments
      └─ outros serviços

Next.js não substitui RabbitMQ nem torna automaticamente um sistema distribuído. Porém, quando roda como servidor, pode ser mais um serviço distribuído: terá réplicas, falhas, caches locais, chamadas de rede, timeouts e observabilidade.

Conexão importante: cache em memória de uma instância Next não é automaticamente compartilhado com outra instância. Em ambientes com múltiplas réplicas, decisões de cache também viram decisões distribuídas.

HISTÓRIA DE ENTREVISTA A CONSTRUIR

Não decorar API: defender decisões

"Num laboratório recente, integrei um dashboard Next.js a um backend distribuído.
Primeiro provoquei erros de boundary entre Server e Client Components.
Depois provoquei dado stale por cache e, por fim, rodei múltiplas instâncias para observar que cache local não é estado compartilhado.
A correção dependeu do requisito de freshness: para dados transacionais preferi leitura dinâmica/uncached; para dados tolerantes a staleness, cache + revalidation."
Honestidade: descrever como laboratório/projeto prático. Não apresentar como incidente de produção de uma empresa se isso não aconteceu.
