POR QUE EMPRESAS ADOTAM NEXT.JS

Não é só “React com rotas”

Convençõesrouting, layouts, bundling e otimizações integradas reduzem decisões repetitivas.
Renderingpermite combinar renderização estática, dinâmica, streaming e componentes de servidor.
Menos JavaScriptServer Components permitem manter partes da árvore no servidor e mandar menos JS ao browser.
SEO e performanceHTML pode existir antes da execução de JavaScript no cliente.
Full-stack/BFFRoute Handlers e Server Actions permitem lógica server-side próxima da UI.
Padronização de equipeuma arquitetura comum para projetos React reduz variações entre times.

MODELO MENTAL

React x Next.js

React
  └─ biblioteca/modelo de componentes e UI

Next.js
  └─ framework em cima de React
      ├─ routing
      ├─ rendering no servidor
      ├─ Server Components
      ├─ cache/revalidation
      ├─ Route Handlers
      ├─ build/bundling

Importante: Server Components e SSR não são sinônimos. Server Components definem onde um componente executa e quanto JS vai ao cliente; SSR descreve a geração de HTML no servidor.

EstratégiaModelo mentalTrade-off

SERVER x CLIENT COMPONENTS

A boundary que mais cai em Next moderno

Server Component (default no App Router)
├─ pode buscar DB/API no servidor
├─ pode usar secrets server-side
├─ reduz JS enviado ao browser
└─ não usa useState/useEffect/window/localStorage

Client Component ('use client')
├─ state
├─ event handlers
├─ effects
├─ browser APIs
└─ custom hooks client-side
Heurística: deixar a maior árvore possível no servidor e empurrar 'use client' para ilhas realmente interativas.

LAB EXECUTADO · 16/09/2026

CSR → SSR → Streaming → Hydration

Este bloco foi executado de ponta a ponta no distributed-workshop/next-payments-dashboard. O objetivo foi transformar cada sigla em comportamento observável.

ExperimentoO que foi quebrado/observadoConclusão comprovada
Server/Client boundaryuseState foi colocado diretamente em page.tsx, gerando Build Error por uso de API client em React Server Component.page.tsx é Server Component por padrão; 'use client' define uma fronteira cliente. A solução preferida foi extrair apenas o Counter interativo.
CSR + CORSPaymentsClient usou useEffect para chamar http://localhost:3001/payments/debug. O browser bloqueou a resposta por ausência de Access-Control-Allow-Origin.CORS é uma política aplicada pelo browser. O request client-side expõe a chamada ao backend no Network e cria acoplamento direto Browser → serviço.
Server-side fetchA mesma leitura foi movida para Server Component. O request direto para :3001 desapareceu do Network do browser e os dados continuaram aparecendo.O fluxo virou Browser → Next → Payments. A chamada server-to-server não está sujeita à barreira CORS do browser.
SSR comprovadoO HTML retornado por curl http://localhost:3002 já continha dados de pagamentos, sem browser nem useEffect.Rendering request-time no servidor pode entregar HTML já baseado nos dados.
Latência distribuídaO endpoint de Payments recebeu ?delayMs=5000. Chamada direta mediu real 0m5.251s. Antes do streaming, TTFB: 5.093562s e TOTAL: 5.093915s.Um await lento no topo da página pode bloquear a resposta inteira; o serviço mais lento passa a dominar o TTFB.
Suspense + StreamingO fetch lento foi movido para PaymentsServer, envolvido em <Suspense fallback=...>. O shell/fallback passou a chegar antes de Payments finalizar; TTFB ficou menor que o tempo total.Streaming não reduz a latência do Payments; isola a latência e permite liberar partes prontas da UI antes da dependência lenta.
Hydration mismatchUm Client Component renderizou Math.random() diretamente, fazendo o primeiro valor do servidor divergir do primeiro render do browser.O primeiro render cliente precisa ser compatível com o HTML inicial. Valor não determinístico durante render pode quebrar hydration.
Correção da hydrationO valor aleatório passou a ser criado em useEffect após um primeiro render determinístico com estado null.Servidor e primeiro render cliente ficaram iguais; só depois da hidratação o estado client-side mudou.
Prova objetiva: antes do Suspense, TTFB ≈ TOTAL ≈ 5s. Depois, o primeiro chunk passou a ser liberado antes do término da dependência, enquanto o tempo total continuou refletindo os ~5s de Payments.
Antes do streaming
Browser/curl → Next → await Payments (5s) → primeiro byte + resposta

Com Suspense
Browser/curl → Next → shell + fallback
                    └─ Payments continua por ~5s
                       └─ chunk final com dados
Insight de sistemas distribuídos: não tornamos Payments mais rápido. Impedimos que a latência de Payments se tornasse automaticamente a latência de toda a página.

BFF

Backend for Frontend

Browser Web ──→ Web BFF ──→ Orders / Payments / Customers
Mobile App  ──→ Mobile BFF ──→ mesmos serviços de domínio

O BFF é uma camada backend criada para as necessidades específicas de uma interface. Pode agregar respostas, adaptar formatos, lidar com cookies/tokens e reduzir acoplamento entre UI e vários serviços internos.

Não é obrigatório: adiciona deploy, observabilidade e um salto de rede. Faz sentido quando clientes diferentes têm necessidades diferentes ou quando a UI precisa compor muitos serviços.

MICROFRONTENDS

O equivalente conceitual dos microsserviços no frontend — com ressalvas

Frontend monolítico
└─ uma aplicação React
   └─ um build/deploy principal

Microfrontend
└─ produto composto por aplicações frontend independentes
   ├─ Orders MFE
   ├─ Payments MFE
   └─ Account MFE

Shell / Host
├─ compõe navegação/layout
├─ carrega os MFEs
└─ entrega ao usuário uma experiência única

A motivação principal não é “performance” nem “usar tecnologia moderna”. É permitir que partes do produto, normalmente alinhadas a domínios e equipes, possam evoluir e ser implantadas de forma independente.

Custos: dependências duplicadas, consistência visual, roteamento entre aplicações, autenticação, contratos, comunicação entre MFEs, observabilidade, testes integrados e maior complexidade operacional.

MODULE FEDERATION

Uma forma de compor microfrontends em runtime

Host / Shell
  ├─ carrega remote Orders
  ├─ carrega remote Payments
  └─ compartilha dependências selecionadas (ex.: React)

Module Federation permite que uma aplicação exponha módulos e outra os consuma, inclusive de builds/deploys separados. É uma ferramenta possível para microfrontends, não a definição de microfrontend.

Distinção de entrevista: microfrontend é a arquitetura/organização; Module Federation é uma técnica de composição e compartilhamento de módulos.

MICROFRONTEND + BACKEND DISTRIBUÍDO

Onde as duas arquiteturas realmente se encontram

Browser
  ↓
Shell
  ├─ Orders MFE ──→ Orders BFF ──→ Orders Service
  ├─ Payments MFE → Payments BFF → Payments Service
  └─ Account MFE ─→ Account BFF ─→ Account Service
                                      ↓
                              eventos / mensageria

Uma organização pode alinhar uma equipe vertical a um domínio: UI + BFF + serviço de domínio + banco/infra. Isso aumenta autonomia, mas só vale o custo quando produto e organização realmente precisam dessa independência.

NEXT.JS + SISTEMAS DISTRIBUÍDOS

Eles se encontram na borda do sistema

Browser
   ↓
Next.js
   ├─ SSR / Server Components
   ├─ BFF / Route Handlers
   ├─ auth/session
   ├─ cache
   └─ agregação de dados
          ↓
   NestJS / APIs / microsserviços

Next.js não substitui RabbitMQ nem torna automaticamente um sistema distribuído. Porém, quando roda como servidor, também terá réplicas, falhas, caches locais, chamadas de rede, timeouts e observabilidade.

Conexão importante: estado/cache local de uma instância não deve ser presumido como estado global compartilhado.
