## Notas teóricas da sessão (consolidar em theory.json preservando IDs)
- Working tree, index e HEAD são estados locais; clean não significa sincronizado.
- Branch é referência móvel a commit, que referencia snapshot; HEAD normalmente referencia a branch atual.
- Upstream é relação configurada; origin/main é referência local de rastreamento, não consulta em tempo real.
- ls-remote consulta refs do servidor sem atualizar refs locais nem baixar histórico.
- fetch baixa objetos ausentes e atualiza refs conforme refspec; no caso observado atualizou origin/main, sem integrar branch ativa. Objetos não equivalem a arquivos ou commits.
- Behind 11 indica 11 commits alcançáveis pelo upstream e não pela branch local; não equivale a 11 arquivos. --no-pager desativa o paginador nesta execução.
- O histórico Git é um DAG: commits apontam para seus pais, podendo ter mais de um em merges. Branches divergentes possuem commits exclusivos de cada lado a partir de ancestral comum. Divergência não implica conflito de arquivos. --graph representa relações; --decorate identifica refs. Limitar histórico com intervalo quando pertinente.
- Merge base é um melhor ancestral comum entre commits; pode haver mais de um em históricos complexos. git merge-base consulta o grafo sem integrar históricos ou alterar refs. Neste caso a base é a main local 9ef37e2.
- Three-way merge considera base comum e os snapshots das duas pontas; divergência sozinha não prova conflito.
- git diff --name-status A..B compara os snapshots de A e B; A (adicionado), M (modificado), D (excluído), podendo haver outros estados. Quantidade de commits não determina quantidade de caminhos com diferença líquida. Arquivos locais observados: README.md, docs/index.html, docs/production-engineering/{CODEX.md,PROGRESS.md,README.md,curriculum.json,index.html,render-panel.cjs,theory.json}.
- Comparar os dois diffs contra a mesma base permite identificar sobreposição de caminhos. Alterar o mesmo arquivo não implica conflito: depende das mudanças, e mesmo sem conflito textual pode haver inconsistência semântica. Neste caso remoto alterou docs/concursos/concursos.json, docs/connect-lab/PROGRESS.md, docs/engineering-notebook.html e adicionou docs/production-engineering/EXPANSION-2026-11-27.md; interseção observada vazia.
- git switch -c cria uma referência de branch e seleciona a nova branch; sem start-point explícito, usa o HEAD atual. Não cria commit. A branch de entrega fica preservada. A grafia efetiva da nova branch contém um erro; corrigir via git branch -m, sem forçar.
- git branch -m renomeia a referência, preservando o commit apontado; o nome de branch não integra o objeto commit. -M força renomeação e pode substituir destino existente; não necessário neste caso.
- Pre-merge check distingue precondição esperada de evidência observada. Conferir branch, HEAD, index/working tree e ausência de operação pendente antes de integrar.
- Merge controlado: git merge --no-commit --no-ff origin/main prepara a integração na branch atual e, se bem-sucedido, para antes do commit. --no-ff evita fast-forward (que --no-commit sozinho não impede). Revisar index e working tree com git status e git diff --cached antes de consolidar. Em conflito, parar e diagnosticar; git merge --abort pode restaurar o estado anterior ao merge, especialmente com árvore inicialmente limpa. Não atribuir domínio nem presumir sucesso.
- MERGING indica operação pendente; Git status pode dizer All conflicts fixed mesmo quando não houve conflitos. Merge automático sem conflitos não garante consistência semântica. git diff --cached --stat resume diferenças entre HEAD e index; git diff sem --cached compara working tree e index, podendo ficar vazio mesmo com mudanças staged.
- --stat resume inserções e exclusões por caminho, não valida conteúdo ou semântica. git diff --cached --name-status e --stat inspecionam o index contra HEAD. O separador -- permite restringir o diff a caminhos; o patch usa linhas + e -, contexto e cabeçalhos de hunks. Revisar mudanças antes de consolidar.
- Git diff tradicional é orientado a linhas: uma linha HTML longa pode gerar um patch extenso mesmo com apenas uma inserção e uma exclusão. git diff --word-diff=plain --unified=0 pode facilitar a leitura, mas não garante saída curta; [-texto-] indica remoção e {+texto+} inserção. Não confundir revisão conceitual com revisão efetiva.
- Pré-commit: git diff --cached --check detecta marcadores de conflito introduzidos e erros de whitespace; git diff --cached --exit-code origin/main -- caminhos compara o conteúdo staged dos caminhos selecionados com a referência remota conhecida (0 se iguais). Verificação de identidade não substitui validação semântica. Merge commit deve ter dois pais, HEAD anterior primeiro e MERGE_HEAD segundo, verificáveis por git log -1 --format='%h %p %s'.
- Merge commit 91f8e50 contém dois pais na ordem ba256c7 (HEAD anterior) e 37ea052 (MERGE_HEAD anterior). Ambos os históricos permanecem alcançáveis. git rev-list --left-right --count A...B conta commits exclusivos de cada lado, na ordem esquerda/direita; não conta arquivos. A referência origin/main pode ficar desatualizada após fetch.
- A contagem 9 0 indica que origin/main conhecido é ancestral de HEAD; não garante que o servidor remoto não tenha avançado. Um push futuro exige verificar a referência atual e respeitar proteção de branch. Reteste de ls-remote deve distinguir consulta ao servidor de atualização de refs locais.

### Notas operacionais
- package.json scripts funcionam como interface operacional do projeto. Inspecionar antes de executar; start usa artefato compilado, migrate/seed são operações de escrita distintas, db:up inicia PostgreSQL em background e aguarda running/healthy conforme configuração. Não presumir que DB saudável implica API saudável. Não repetir seed ou migrations sem conhecer alvo e efeitos. Verificar bindings e isolamento antes de iniciar.
- Git Bash no Windows pode ter aliases/wrappers TTY incompatíveis com pipes. Alternativa de inspeção: Node.js execFileSync('docker.exe', args, {encoding:'utf8'}) captura stdout diretamente, sem alias do shell; não imprimir config completa (pode conter secrets). Confirmar resultado antes de atribuir causa. docker compose ps -a vazio não prova ausência de containers em outros projetos.
- Docker port publishing: host_ip 127.0.0.1 limita a porta publicada a loopback no host; published 54329 é porta do host, target 5432 é porta do container. Volume nomeado desacopla persistência do ciclo de vida do container. Digest fixa identidade do artefato, não garante segurança. Status vazio não prova ausência de volume ou de outros processos. Healthcheck do banco não prova saúde da aplicação.
- Startup por dependências: healthcheck de PostgreSQL comprova apenas a condição configurada, não autenticação do backend, esquema atualizado ou funcionamento de fluxos. Consultar catálogo de tabelas existentes sem alterar dados; inspecionar configuração efetiva do backend sem imprimir credenciais e compilar antes de executar. Evitar seed/migrations até verificar alvo e necessidade.
- Build produz artefatos JavaScript; npm start executa dist/main.js, portanto pode rodar regra antiga sem recompilar. Schemas PostgreSQL organizam namespaces, não garantem isolamento/autorização por si. Contagem de tabelas não garante migrations atuais. Binding local explícito na API. Validar URL efetiva sem revelar credenciais, comparar nome do banco com POSTGRES_DB do container e restringir host/porta; só então build e startup.
